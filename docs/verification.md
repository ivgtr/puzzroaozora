# 原稿修復机の検証記録

対象: Issue #1 / PR #5。自動で確認できる仕様と、人間の体験評価を区別する。

## 自動検査

Node標準テスト9件（`tests/model.test.ts` / `tests/text.test.ts`）。2/3/4枚確定、前後追加、端数、仮組みの保護、分離・Undo・座標、同文交換、塊ID、原文一致、graphemeと方眼、有限の候補生成、取り込みURLと外字を確認する。

型、lint、本番buildは通常のnpmコマンドを使用する。検証用Actionsは作業ブランチだけの一時的なものであり、最終差分には残さない。多端末のマトリクスや大量シードを恒常CIに追加しない。

実行結果はPRの検証節へ記録する。実行前の項目を成功として扱わない。

## ブラウザで確認する代表経路

デスクトップと小画面で、1つのCanvas上の本棚→初読→組立→完成を確認する。原文を隠した時は読み上げ用DOMにも残さない。正しい組立、仮組みとUndo、原文見直し、ズーム、入力の取消を少数の代表操作で扱う。

取り込みは成功と失敗を分け、旧レコードが失敗時に保存されていることを確認する。字形/フォント読込失敗は原文を置換せず再試行へ進むことを確認する。APIフィクスチャの確認を外部APIでの実作品取得成功と混同しない。

## 人間による確認が必要な事項

- 実物のマウス/タッチ、実端末のDPIで22px本文・29px方眼が読みやすいか。
- 横組と縦組の実機比較、約物・小書き仮名・外部作品の個別字形の最終確認。
- 仮組みを残す体験と、新規2/3/4枚の難易度が文章量・分割に見合っているか。
- 音量、耳障りさ、追加と塊連結と完成の区別。生成波形の存在を聴感の合格とはしない。
- 旧仮名や固有名詞に対する自動分割の良問としての妥当性。

これらの人間プレイ/聴取を実施したと報告しない。必要な調整はこの記録と原稿の開発メモを根拠に行い、判定ロジックのフォールバックや巨大な検査基盤を追加しない。
