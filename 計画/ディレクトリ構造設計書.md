# ディレクトリ構造設計書

## 1. 概要

本書は、青空パズルプロジェクトのディレクトリ構造とファイル配置を定義したものです。
Next.js Pages Routerのベストプラクティスに従い、機能ごとに適切に分離された構造を採用します。

## 2. プロジェクトルート構造

## 6. 各ディレクトリ・ファイルの役割

### 6.1 ルートレベル設定ファイル

| ファイル | 役割 |
|---------|------|
| `.env.local` | ローカル環境変数（APIキー、エンドポイント等） |
| `.env.example` | 環境変数のテンプレート（開発者向け） |
| `next.config.ts` | Next.jsの設定（リライト、リダイレクト、webpack設定等） |
| `tsconfig.json` | TypeScriptコンパイラ設定、パスエイリアス |
| `tailwind.config.ts` | Tailwind CSSのカスタマイズ設定 |
| `jest.config.js` | Jestテスト設定 |

### 6.2 src/pages（ルーティング）

| ディレクトリ/ファイル | 役割 |
|----------------------|------|
| `index.tsx` | ランディングページ、ゲーム説明、スタートボタン |
| `game.tsx` | メインゲーム画面、パズル操作UI |
| `result.tsx` | 結果表示画面、スコア、次のゲームへの導線 |
| `api/puzzle/generate.ts` | パズル生成エンドポイント |
| `api/puzzle/submit.ts` | 解答提出・判定エンドポイント |
| `api/books/list.ts` | 青空文庫作品リスト取得 |

### 6.3 src/components（UIコンポーネント）

| ディレクトリ | 役割 |
|-------------|------|
| `common/` | 全画面で共通利用されるコンポーネント |
| `game/` | ゲーム画面専用のコンポーネント |
| `result/` | 結果画面専用のコンポーネント |

#### 主要コンポーネントの詳細

**GameHeader**
- ゲームタイトルの表示
- 難易度バッジ（Normal/Easy/Hard）の表示
- ゲームモードバッジ（完答のみ/通常モード）の表示
- コンパクトで見やすいヘッダーレイアウト

**GameInfoBar**
- 問題進捗の表示（例：問題: 1/10）
- 現在の得点をリアルタイム表示
- 効果音ON/OFFトグル
- 簡単モードON/OFFトグル
- 横一列の情報バーレイアウト

**AnswerArea**
- 破線で囲まれたドロップゾーン
- ドラッグ&ドロップで形態素を配置
- 配置済み形態素の順序変更機能
- 形態素をクリックで元に戻す機能
- 空の状態では「ここに並べてください」等のプレースホルダー表示

**SegmentPool**
- シャッフルされた形態素をグリッド表示
- フレキシブルなグリッドレイアウト
- 選択された形態素は非表示またはグレーアウト
- レスポンシブ対応（画面幅に応じて列数調整）

**SegmentChip**
- カラフルな角丸ボタンスタイル
- 品詞に応じた背景色（名詞：黄色、動詞：ピンク、助詞：青など）
- クリック/タップで選択
- ドラッグ可能な実装
- ホバー/フォーカス時のアニメーション
- 文字サイズの自動調整

**GameActions**
- クリアボタン：解答エリアをリセット（グレー背景）
- 答え合わせボタン：解答を提出（緑背景、目立つデザイン）
- スキップボタン：次の問題へ（青背景）
- ボタンの活性/非活性状態の制御

**ToggleSwitch**
- iOS風のトグルスイッチデザイン
- スムーズなON/OFFアニメーション
- ラベル付きで用途を明示
- アクセシビリティ対応

**DragDropProvider**
- react-beautiful-dndまたはreact-dnd使用
- ドラッグ中のビジュアルフィードバック
- タッチデバイス対応
- ドロップ可能エリアのハイライト

### 6.4 src/lib（ビジネスロジック）

| ディレクトリ | 役割 |
|-------------|------|
| `aozora/` | 青空文庫データの取得・パース処理 |

#### 主要モジュールの詳細

**aozora/parser.ts**
- 青空文庫の特殊記法（ルビ、注記）の処理
- テキストの正規化、抽出

**tokenizer/index.ts**
- 形態素解析の実行
- 難易度に応じた分割ルールの適用

**puzzle/generator.ts**
- パズルデータの生成
- シャッフル処理
- シード値による再現可能な生成

**puzzle/validator.ts**
- ユーザー解答の検証
- 正解判定ロジック

## 7. 命名規則

### 7.1 ファイル名

- **コンポーネント**: PascalCase（例：`SegmentCard.tsx`）
- **ユーティリティ**: camelCase（例：`parser.ts`）
- **型定義**: camelCase（例：`types.ts`）
- **設定ファイル**: kebab-case（例：`api.config.ts`）
- **テストファイル**: `*.test.ts` または `*.spec.ts`

### 7.2 ディレクトリ名

- **基本**: kebab-case（例：`game-controls`）
- **コンポーネント**: PascalCase（例：`SegmentCard/`）

### 7.3 エクスポート

- **default export**: コンポーネント、ページ
- **named export**: ユーティリティ関数、型定義、定数

## 8. インポートパスエイリアス

`tsconfig.json`で以下のエイリアスを設定：

```json
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"],
      "@components/*": ["./src/components/*"],
      "@lib/*": ["./src/lib/*"],
      "@hooks/*": ["./src/hooks/*"],
      "@contexts/*": ["./src/contexts/*"],
      "@types/*": ["./src/types/*"],
      "@styles/*": ["./src/styles/*"],
      "@config/*": ["./src/config/*"],
      "@data/*": ["./src/data/*"]
    }
  }
}
```

使用例：
```typescript
import { SegmentCard } from '@components/game/SegmentCard';
import { parseAozoraText } from '@lib/aozora/parser';
import { PuzzleData } from '@types/puzzle';
```

## 9. 開発フロー

### 9.1 新機能追加時

1. 型定義を`src/types/`に追加
2. ビジネスロジックを`src/lib/`に実装
3. カスタムフックを`src/hooks/`に作成
4. UIコンポーネントを`src/components/`に実装
5. ページに統合
6. テストを`tests/`に追加

### 9.2 APIエンドポイント追加時

1. 型定義を`src/types/api.ts`に追加
2. ハンドラーを`src/pages/api/`に実装
3. クライアント側のフックを作成
4. 統合テストを追加

## 10. ビルド最適化

### 10.1 コード分割

- 動的インポートを使用してバンドルサイズを削減
- kuromoji.jsの辞書ファイルは遅延読み込み

### 10.2 静的生成

- 作品リストなどの静的データはビルド時に生成
- `getStaticProps`を活用

### 10.3 画像最適化

- Next.js Imageコンポーネントを使用
- WebP形式への自動変換

## 11. セキュリティ考慮事項

### 11.1 環境変数

- APIキーは`.env.local`に保存
- クライアント側で使用する変数は`NEXT_PUBLIC_`プレフィックス

### 11.2 入力検証

- APIエンドポイントで必ず入力検証
- XSS対策のためのサニタイゼーション

### 11.3 レート制限

- API Routesでレート制限を実装
- キャッシュを活用して負荷軽減

## 12. まとめ

この構造により、以下のメリットが得られます：

1. **保守性**: 機能ごとに明確に分離された構造
2. **拡張性**: 新機能追加時の影響範囲を最小化
3. **テスタビリティ**: ロジックとUIの分離によるテストの容易さ
4. **パフォーマンス**: 適切なコード分割とキャッシュ戦略
5. **開発効率**: 明確な命名規則とディレクトリ構造
